<assumption_delta_decision>
**Noun that is now primary:** the per-client `whatsapp_instance` — `client_id` (unique), `instance_name`
(`livia_client_<id>`, deterministic), and its own encrypted `token`. Before this phase, "the Evolution
credential" meant exactly one thing: the global manager `apikey` from `Evolution.global_api_key`
(`config/initializers/evolution.rb`, phase 25) — one apikey, one implicit "instance" (the whole
manager). This phase introduces a genuine second axis: N per-client instances, each with its own
`instance_name` + `token`, living under one shared manager.

**Decision: `add-alongside` (not `promote`).** The global `apikey` is NOT superseded and is NOT demoted
to a legacy fallback — it keeps doing exactly what it did in phase 25 (`fetch_instances`,
`connection_state`, and now also `create_instance`/`connect`/`set_webhook` as the manager-level
credential). What changes is its *role label*: from phase 26 forward it is the **provisioning
credential only** — the key used to CREATE/ADOPT/CONFIGURE instances at the manager. It is never used
to send or read anything scoped to a specific client's WhatsApp number; that per-client scope is what
`whatsapp_instance.token` now owns (send/read is phases 28/29, out of scope here). The two credentials
answer different questions ("can I manage instances on this manager?" vs. "which WhatsApp number is
this?") and neither one can derive the other, so `add-alongside` is correct — there is no old singular
representation to migrate away from, only a new axis to add next to it.

**Accepted debt / promotion trigger:** none expected. If a future milestone needs multi-manager Evolution
(more than one shared host), THAT would be the next assumption-delta moment — `Evolution.global_api_key`
would need to become per-manager, and `whatsapp_instance` would need a `manager_id` foreign key. Not
anticipated in v1.7; noted here only so a future planner does not have to re-derive it.

**Suggested invariant test (optional, not required this phase):** "every controller/service that reads
or writes a specific client's WhatsApp state resolves the instance via `@client.whatsapp_instance` /
`WhatsappInstance.evolution_name_for(client)` — never a bare `WhatsappInstance.find` or a hardcoded
name." `test/models/whatsapp_instance_test.rb` in Task 1 below asserts `evolution_name_for` is
deterministic per client id, which is the load-bearing half of this invariant; the "never
`WhatsappInstance.find(params[:id])`" half is enforced by code review across 26-01..26-05 (see
Anti-pattern in `26-PATTERNS.md`), not by a standalone test.
</assumption_delta_decision>
