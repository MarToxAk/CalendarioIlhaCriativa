# Code Review: Phase 31 — Instância WhatsApp Compartilhada entre Clientes

## Summary

Phase 31 de-uniqueifies `whatsapp_instances.instance_name` so multiple `WhatsappInstance` rows (one per client) can point at the same physical Evolution/WhatsApp connection, while keeping `client_id` UNIQUE. The core cross-client isolation boundary (SEG-04) holds up well after this change: every isolation-sensitive path (`client.divulgacoes.find`, `client.whatsapp_instance.whatsapp_groups.where(active:).find`, `SendToGroupJob`'s token/instance resolution) is anchored on the `WhatsappInstance`/`Divulgacao` **row id**, never on the now-shared `instance_name`, and `test/integration/cross_client_isolation_test.rb` gained exactly one new test (Test 4) proving this survives sibling sharing — the three pre-existing tests are byte-identical except for a backward-compatible `instance_name: nil` keyword default added to the shared `build_client_with_whatsapp!` helper. `Evolution::InstanceProvisioner#reuse` copies the encrypted `token` only through the AR attribute (never through raw SQL or logs), and `SendToGroupJob.limits_concurrency`'s key was correctly moved from `whatsapp_instance.id` to `instance_name` so two sibling clients sharing a connection can never send concurrently (ENVIO-09), with a documented, tested fallback for the unreachable-today "no instance" branch.

The issues found are all in newly-introduced fan-out/race territory the phase itself calls attention to: the webhook fan-out (`Webhooks::EvolutionController#create`) has no per-sibling exception isolation, so one failing sibling update can abort the loop and silently strand the rest at a stale `connection_state`; the manual "Sincronizar grupos" guard/throttle in `Admin::WhatsappGroupsController#sync` is still keyed per `WhatsappInstance` row id rather than per shared `instance_name`, so two sibling clients can each pass their own guard and run `Whatsapp::GroupSynchronizer` concurrently with different `batch_started_at` values, racing the deactivation pass; and the "Parear novamente" confirmation modal was not updated to warn that reconnecting now disrupts every sibling client sharing the same physical connection, not just the one being viewed. None of these break the cross-tenant security boundary — they are correctness/UX gaps in the new shared-connection concurrency model.

## Findings

### Critical
None.

### Warning

**app/controllers/webhooks/evolution_controller.rb:22-27** — The sibling fan-out (`siblings.find_each { |instance| apply_event(instance) }`) has no per-row rescue. `apply_connection_update` (line 74, `instance.save!`) and `apply_qrcode_updated` (line 83, `instance.update!`) can raise (e.g. a validation or DB constraint failure on one sibling row), which aborts `find_each` mid-loop: siblings already processed keep their new state (no wrapping transaction to roll them back), siblings not yet reached keep their stale `connection_state`/`last_qr_base64`, and Evolution receives a 500 instead of `:ok` for an event that was actually *partially* applied. This directly matches the risk called out in the phase background ("doesn't silently drop an update if the loop partially fails") — today it can. Suggest wrapping each `apply_event(instance)` call in its own `begin/rescue` (log + continue) so one bad sibling row never blocks the others, and/or wrapping the whole loop in a transaction if all-or-nothing semantics are preferred instead.

**app/controllers/admin/whatsapp_groups_controller.rb:24-38** (guard) and **app/services/whatsapp/group_synchronizer.rb:21-65** (fan-out) — The manual-sync throttle/guard is scoped per `WhatsappInstance` **row**, not per shared `instance_name`/physical connection: the cache key is `"wa_groups_sync_#{@instance.id}"` and the in-progress check is `@instance.groups_sync_syncing?`, both read from the *specific client's row*. With phase 31's sharing, two sibling clients (different `client_id`, same `instance_name`) each have their own row id and their own `groups_sync_state`, so each independently passes the guard and can enqueue its own `Whatsapp::SyncGroupsJob` around the same time. Both resulting `GroupSynchronizer#call` invocations then do their own `fetch_groups` HTTP call (redundant work) and, more importantly, each fans out and rewrites **all** sibling rows' `whatsapp_groups` using its *own* `batch_started_at`. If job A (started at `T1`) and job B (started at `T2 > T1`) interleave, job B's deactivation pass (`where(active: true).where("synced_at < ?", T2)`) can spuriously deactivate a group that job A had just (re)synced with `synced_at = T1` for the same sibling — even though that group is still present in the live Evolution list — because `T1 < T2`. This is exactly the "race-safe" fan-out question raised in the review background; unlike `Whatsapp::SendToGroupJob` (whose `limits_concurrency` key was deliberately moved from row id to `instance_name` for D-04), the analogous protection was not extended to group sync. Suggest keying both the 15s cache throttle and the `groups_sync_syncing?` guard off `instance_name` (or locking across all sibling ids) rather than the single row's id/state.

**app/views/admin/whatsapp_instances/_panel.html.erb:130-146** — The "Parear novamente" (`reconnect`) confirmation modal body ("Parear novamente encerra a sessão atual do WhatsApp deste número. Os disparos ficam indisponíveis até um novo pareamento ser concluído.") was not updated for phase 31: `reconnect` calls `Evolution::Client.connect(inst.instance_name)`, which tears down the *physical* WhatsApp session — and with a shared connection that affects every sibling client using that `instance_name`, not just the one whose panel the admin is looking at. The panel does show a passive "Conexão compartilhada com N cliente(s)" note elsewhere on the page (line 86) when `shared?`, but the destructive-action confirmation itself gives no warning of the blast radius, unlike the "Reutilizar conexão existente" modal (line 65), which does correctly warn about sharing consequences. An admin could unknowingly disconnect WhatsApp for several clients at once. Suggest conditioning the reconnect modal body on `whatsapp_instance.shared?` to include a warning naming the affected sibling count, mirroring the reuse modal's copy.

### Info

**db/migrate/20260831185638_deuniqueify_whatsapp_instance_name.rb:2-5** — `remove_index :whatsapp_instances, :instance_name` followed by a bare `add_index :whatsapp_instances, :instance_name` inside a `change` method is forward-safe, but not cleanly reversible: on `db:rollback`, Rails reverses `add_index` (removes the non-unique index) and then reverses the original `remove_index` by re-adding a *default (non-unique)* index — it does not know the original index was `unique: true`, since that option wasn't recorded anywhere in this migration. A rollback of this migration silently leaves the table without its original uniqueness guarantee. Low risk in practice (nobody is expected to roll this back — the whole point of the phase is to permanently relax the constraint) but worth a one-line comment noting the rollback isn't symmetric, or an explicit `down` method if true reversibility is ever wanted.

**app/controllers/admin/whatsapp_instances_controller.rb:99** — `params.require(:source_instance_name)` raises `ActionController::ParameterMissing` for a blank string, not only a missing key (Rails' `require` calls `.present?`). The `<select>` in the view starts on the blank `include_blank` option and the Stimulus controller disables the submit button until a value is chosen, so this path isn't reachable through the normal UI — but a direct POST with an empty `source_instance_name` (or the param omitted) surfaces Rails' generic 400 error page instead of the same friendly "Conexão indisponível…" alert used for every other invalid-target case in this action. Minor robustness gap; consider `params[:source_instance_name].presence` with an explicit early redirect instead of `require`.

**app/models/whatsapp_instance.rb:48-53** — `shareable_targets` does not filter out connections owned by deactivated (`active: false`) clients; a `connected` `WhatsappInstance` belonging to a client whose portal access has been turned off is still offered as a reuse target for a different client. This is likely intentional (the physical connection is still real and usable regardless of the owning client's portal status), but worth a quick confirmation that reusing a deactivated client's connection is a supported scenario rather than an oversight.
