<objective>
Establish the Divulgação schema, models, route surface, and a working end-to-end
creation happy path — the thinnest vertical slice through every layer this phase
touches — plus the canonical cross-client isolation proof.

An admin can open `admin/clients/:client_id/divulgacoes/new`, pick an approved
arte of that client, check one or more of that client's active WhatsApp groups,
choose a send date/time, submit, and land on a persisted Divulgação whose
per-group rows are all `pendente` with the group name frozen as it was
(DIVU-01, DIVU-09). Every id from the form is re-resolved through the client
association so a foreign or inactive id is refused, not leaked (SEG-01, SEG-02).

Purpose: The two-table schema is the most expensive thing in this milestone to
get wrong — phase 29's send engine reads `divulgacoes.status` and the frozen
`divulgacao_grupos` snapshot. Proving the whole slice end-to-end now catches an
architectural dead-end after one commit instead of after the validations,
preview, and detail page are already built on top of it.

Output: 2 migrations, the `Divulgacao`/`DivulgacaoGrupo` models, the nested
route (full surface incl. `patch :cancel`), `Admin::DivulgacoesController`
(`#new`/`#create`/`#index`), a happy-path `new.html.erb` + minimal
`index.html.erb`, and the A×B cross-client test.

## Planner assumptions (unresolved items surfaced from 28-UI-SPEC)

- **Picker selection persisting across paginated pages** — carried from Phase 27
  as ⚠ unresolved. This plan mitigates but does not eliminate it by NOT
  paginating the in-form picker: `render "admin/whatsapp_groups/picker"` is
  called with no `groups:`/`pagy:`, so the partial renders every active group
  and `#create` resolves the full submitted array. The agency's clients are
  expected to have well under 25 active groups. If a client ever exceeds a
  workable single-page list, hidden inputs for off-page selections (or "load all
  when the count is small") is an assumption the planner must resolve then — it
  is NOT designed here.
- **`WHATSAPP_MEDIA_MAX_BYTES = 16.megabytes`** (used from plan 02) is a
  conservative heuristic (RESEARCH Assumption A1); phase-29 UAT measures the real
  Evolution/Cloudflare gateway ceiling (5/15/20/30 MB probe) and the constant is
  a one-line update if wrong.
- **`WHATSAPP_SEND_DELAY_MIN_SECONDS` / `_MAX_SECONDS`** (introduced in plan 03)
  have no repo precedent (RESEARCH Assumption A2) — phase 29 (ENVIO-02) owns the
  canonical read and must honor these names or rename in the single place
  (`Divulgacao::SEND_DELAY_MIN`/`MAX`).
