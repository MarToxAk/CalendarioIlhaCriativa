# Requirements Archive — v1.6 API JSON

**Status:** ✅ SHIPPED 2026-06-13
**Archived:** 2026-06-13

---

## Contexto

Expor uma API JSON para dois consumidores principais:
- **App mobile** (admin e cliente) — substitui/complementa o portal web
- **IA** — lê aprovações, insere artes, envia notificações/resumos

A autenticação usa três modos distintos (ver nota `.planning/notes/api-auth-strategy.md`).

---

## Requisitos (todos implementados)

### Autenticação (AUTH)

- [x] **AUTH-01**: Admin autentica na API com e-mail e senha e recebe JWT — Phase 21 ✓
- [x] **AUTH-02**: JWT de admin tem expiração configurável (padrão 24h) — Phase 21 ✓
- [x] **AUTH-03**: Cliente autentica na API com access_token do portal + senha e recebe um JWT de cliente (usado como Bearer) — Phase 21 ✓
- [x] **AUTH-04**: IA autentica com API key dedicada via header `Authorization: Bearer <api_key>` — Phase 21 ✓
- [x] **AUTH-05**: Requisições sem autenticação válida retornam 401 com mensagem estruturada — Phase 21 ✓

- [x] **APIADM-01**: Admin lista clientes (paginado) — Phase 22 ✓
- [x] **APIADM-02**: Admin cria novo cliente — Phase 22 ✓

- [x] **APIADM-04**: Admin cria nova arte (upload de imagem incluído) — Phase 22 ✓
- [x] **APIADM-05**: Admin vê histórico de aprovações — Phase 22 ✓

---

## Out of Scope (v1.6 — mantido)

- WebSockets / push notifications nativas mobile — cobre a IA via polling
- GraphQL — REST é suficiente para os casos de uso identificados
- OAuth / social login — token do portal basta para o cliente
- Documentação interativa (Swagger/OpenAPI) — pode ser adicionada em v1.7
- SDK cliente — consumidores implementam diretamente contra REST
