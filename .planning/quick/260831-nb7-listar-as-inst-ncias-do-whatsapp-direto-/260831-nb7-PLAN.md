<objective>
Trocar a FONTE do `<select>` "Reutilizar conexão existente" (painel WhatsApp de
`admin/clients#show`): hoje ele lista só linhas locais `WhatsappInstance`
(`connection_state: connected`) via `WhatsappInstance.shareable_targets`; passa
a listar TODAS as instâncias que `Evolution::Client.fetch_instances` (GET
`/instance/fetchInstances`, já existente) reporta como conectadas — inclusive
instâncias que existem no Evolution mas ainda não têm NENHUMA linha
`WhatsappInstance` local (decisão travada do usuário, não é reinterpretável).

**Por que isso quebra o desenho zero-I/O de `InstanceProvisioner#reuse`
(fase 31, D-07):** `#reuse(existing:)` copia campos de uma linha AR irmã já
existente, sem chamada de rede. Quando o admin escolhe uma instância que o
Evolution reporta mas que NENHUMA linha local referencia ainda, não existe
irmã AR pra copiar. A solução adotada (opção b do brief, a que reusa mais
código e toca menos arquivos): esse caso vira exatamente o mesmo caminho de
**adoção** que a fase 26 já usa quando `create_instance` colide com "already
in use" — `InstanceProvisioner#adopt(name, headers)` já é genérico em `name`
(busca em `fetch_instances`, `set_webhook` SEMPRE, lê `connection_state`,
persiste via `find_or_initialize_by(client: @client)`); só precisa ficar
alcançável por fora do rescue de `#call`. `#reuse(existing:)` continua
intocado (zero I/O preservado, D-07 não muda) para o caso com irmã local.

**Risco documentado, não bloqueante:** o nome do campo por-instância que
`GET /instance/fetchInstances` devolve para o estado de conexão
(`connectionStatus`, por `.planning/research/FEATURES.md:119`, lido do
schema Prisma do Evolution) nunca foi confirmado empiricamente — só o
round-trip agregado (`Array` de 6, HTTP 200) foi provado no EVO-01/25-04
(`.planning/notes/evolution-contract.md`). O curioso é que `InstanceProvisioner#adopt`
já existente NUNCA confiou nesse campo (sempre faz uma chamada separada a
`connectionState`) — sinal de que o campo pode não ter sido validado quando
26-02 foi escrito. Task 1 abaixo abre com um smoke check ao vivo (credenciais
já configuradas, EVO-01 fechado) pra confirmar o campo antes de codificar o
filtro em cima dele.

**Risco de superfície aceito, não corrigido aqui:** o Evolution é um manager
COMPARTILHADO com outras apps da agência (`InstanceProvisioner` já documenta
isso). Como a decisão travada é listar TODAS as instâncias que o Evolution
reporta (não só as já vinculadas a um cliente local), o `<select>` pode
mostrar — e o fluxo de adoção pode reivindicar — uma instância que não
pertence a este app. Aceito porque: (a) é decisão explícita do usuário, não
desta fase; (b) toda a superfície (`admin/clients#show`, `#reuse`) já é
admin-only (`Admin::BaseController`); (c) nenhum token/segredo aparece no
`<select>` (só `instance_name` + nomes de cliente).

Purpose: o admin vê no `<select>` QUALQUER conexão WhatsApp já pareada que o
Evolution conhece agora, não só as que algum cliente local já reivindicou —
inclusive instâncias "órfãs" no Evolution que nenhum cliente local usa ainda.
Output: `WhatsappInstance.shareable_targets` passa a ser Evolution-backed com
degradação graciosa (erro de rede -> lista vazia, nunca 500);
`InstanceProvisioner#adopt_named` expõe o caminho de adoção da fase 26 para
um nome arbitrário; `Admin::WhatsappInstancesController#reuse` decide entre
copiar de uma irmã local (zero I/O, D-07 intocado) ou adotar ao vivo.
</objective>
